## 一、範圍

| 階段 | 實體 | 說明 |
|---|---|---|
| **第一階段** | **據點**（Node） | 有位置的店家、工廠、設施、社區據點 |
| **第一階段** | **資源**（Resource） | 據點能提供的物料、工具、空間、技能、知識、**運輸** |
| 第二階段 | 需求與供給（Intent） | 「需要 4 片棧板」「有木屑可以給」 |
| 第二階段 | 流動事件（Event） | 試點中實際發生的物質流 |

「人」不建獨立資料表，技能掛在據點或組織底下（個資原則）。

## 二、據點分類：依使用者想做的事（第 2 版）

使用者決定：分類從簡，以直觀需求為主。所以分類問的是「**我想做什麼**」，而不是「這是哪一種行業」。

| 需求分類 | 使用者會問 | 典型據點 |
|---|---|---|
| **買材料** | 哪裡買得到木材、螺絲、防水漆？ | 五金行、建材行、木材行、材料行 |
| **找人做、找人修** | 誰能幫我裁木板、焊鐵架、修電器？ | 工廠、木工、鐵工、修理店、維修中心 |
| **借工具、借空間** | 哪裡借得到電鑽、有地方可以施工？ | 維修中心、創客空間、工具圖書館、閒置空間 |
| **運送** | 怎麼把東西搬過去？ | 貨運、搬家、租車、可借推車或貨運自行車的地方 |
| **回收再利用** | 哪裡有不要的材料、木屑、咖啡渣？ | 回收場、二手店、有邊角料的工坊、咖啡店 |
| **社區據點** | 附近有誰在做類似的事？ | 堆肥站、社區園圃、社區組織 |

**一個據點可以屬於多個分類**（例如維修中心同時是「找人修」和「借工具、借空間」），所以分類存成多值欄位 `needs`，不是單選。地圖篩選也用這六類。

原本的「行業細分類」（五金零售、金屬製品製造……）保留在資料裡當作內部欄位 `source_category`，方便追溯來源，但介面上不呈現。

### 為什麼登記資料這麼「髒」
- **營業項目是「登記可以做的事」，不是「實際在做的事」**。公司登記時常一次登記幾十個營業項目，五金零售、五金批發是很常見的附帶項目，所以地產顧問、租車公司也會出現在名單上。這也解釋了公司登記雜訊特別多。
- **登記地址不一定是營業地點**：可能是負責人住家、會計師事務所或借址登記（CASAS2020 在倫敦也遇到同樣問題）。
- **歇業的不會自動消失**：商業登記裡大約一半是歇業、撤銷或遷出，一定要依狀態篩選。

### 用簡單規則篩選後的結果
規則：營業中，且排除名稱有「貿易、國際、投資、顧問、管理、行銷、科技、資訊、地產、開發……」的。
- **高可信**：名稱看得出相關（五金、建材、水電、鐵、木、玻璃……）**而且**地址在一樓或沒寫樓層。
- **中可信**：名稱相關**或**在一樓，兩者有其一。

| 資料集 | 營業中 | 高可信 | 中可信 |
|---|---|---|---|
| 商業－五金零售 | 1,681 | 157 | 878 |
| 商業－五金批發 | 1,439 | 81 | 602 |
| 商業－建材零售 | 824 | 79 | 397 |
| 公司－五金零售 | 15,920 | 329 | 4,167 |
| 公司－五金批發 | 20,381 | 383 | 4,947 |

高可信的樣本看起來確實是實體店，例如「龍太五金行」「洪記建材行」「巨揚水電行」「建臣五金有限公司」「盛元木工有限公司」；中可信的則混雜了設計公司、工作室、工程行。

### 建議的處理方式
1. **所有登記資料都先過濾營業狀態**，歇業的不收。
2. **依上面的規則給每一筆標上可信等級**，存在 `confidence` 欄位（高、中、低），和 `verification`（是否驗證過）分開。
3. **公開地圖預設只顯示「高可信」和「現地確認」的據點**；中、低可信的放在「顯示更多（未確認）」的開關後面，或只用在示範點周邊的走讀候選清單。這樣既納入公司登記，又不會讓地圖被大量不相關的公司淹沒。
4. **登記工廠**依名稱關鍵字推測類別，推測不出來的標為「其他製造」；特定工廠直接用產業代碼。
5. **社區資源回收站不放上公開地圖**，只在村里概況裡當統計（例如「本里有 3 個大樓自設回收站」）。
6. **OSM 和登記資料互相補**：OSM 有、登記沒有的，可能是用公司名義登記或名稱不同；兩邊都有的，可信度提高。
7. **示範點周邊的走讀是最終的檢驗**，也能回頭校正篩選規則，例如算出「高可信」實際上有多少比例真的存在。

## 六、資料表設計（第 2 版）

### `nodes`
| 欄位 | 說明 |
|---|---|
| `node_id` | 唯一代碼，例如 `gcis-12345678`、`co-12345678`、`fac-63021895`、`osm-n123`、`field-0001` |
| `name`、`address`、`lon`、`lat`、`village_code` | 名稱、地址、座標、所在村里 |
| `needs` | 需求分類，可多選（第二節的六類） |
| `source_category` | 來源的原始分類，例如 `F206010`、`25`、`craft=carpenter` |
| `business_id` | 統一編號（有的話） |
| `since_year` | 開業或登記年（有的話） |
| `status` | 營業中、歇業、未知 |
| `confidence` | 依規則推估的可信度：高、中、低 |
| `verification` | 0 未驗證、1 開放資料、2 現地確認、3 當事人確認 |
| `verified_at` | 最後確認日期 |
| `visibility` | `public`、`aggregate`、`private` |
| `source`、`license` | 來源（可多個）、授權 |

**不收錄**：負責人姓名。

### `resources`
| 欄位 | 說明 |
|---|---|
| `resource_id`、`node_id` | 唯一代碼、所屬據點 |
| `resource_class` | 物料、工具、空間、技能、知識、運輸 |
| `item` | 受控詞表中的項目，例如 `pallets`、`cargo_bike` |
| `access` | 售、借、贈、服務、交換 |
| `note` | 補充，例如「每週六」「需預約」 |
| `source`、`confidence`、`verification`、`verified_at` | 同上 |

### 對照表與詞表
- `data/schema/category_crosswalk.csv`：把來源分類對應到 `needs` 和推論資源。
- `data/schema/resource_items.csv`：資源受控詞表，從堆肥站的需求清單開始建。KoboToolbox 表單的選項也直接用這份詞表，現地資料和開放資料才能用同一套詞。

## 七、處理流程

```
下載 → 篩臺北市、營業中 → 標可信等級 → 地址轉座標（門牌資料）
→ 套用對照表 → 合併重複 → 判斷村里 → 輸出 nodes / resources
→ 示範點周邊：產生走讀候選清單 → KoboToolbox 現地確認 → 匯入、更新驗證等級
```

- **地址轉座標**：用[臺北市門牌位置數值資料](https://data.gov.tw/dataset/155472)，不需申請 TGOS。
- **合併重複**：統一編號相同；或正規化地址相同且名稱相近；或 30 公尺內且名稱相近。

## 八、KoboToolbox 是怎麼運作的

KoboToolbox 是一套免費、開源的現地資料蒐集工具，最早為人道救援與田野調查開發，很多研究團隊和 NGO 在用。

### 角色與元件
| 元件 | 做什麼 | 誰用 |
|---|---|---|
| **網站後台**（kf.kobotoolbox.org 或歐洲站 eu.kobotoolbox.org） | 設計表單、管理專案和成員、檢視與審核資料、匯出 | 你和負責整理資料的人 |
| **KoboCollect App**（只有 Android） | 在手機上填表，可以離線使用、記錄 GPS、拍照 | 走讀的調查員 |
| **網頁表單**（Enketo） | 用手機瀏覽器填表，iPhone 也能用；載入後可以離線填寫 | 沒有 Android 手機的調查員 |

### 一次調查的流程
1. **設計表單**：在後台用拖拉式編輯器，或用 Excel 寫成 XLSForm（一種固定格式的試算表）。建議用 XLSForm，因為可以直接把我們的資源詞表貼成選項，也方便放進 Git 管理版本。
2. **部署**：在後台按「部署」，表單就會出現在團隊成員的手機上。之後修改表單要重新部署，舊資料會保留。
3. **走讀填寫**：每到一個據點填一份。可以設計成：
   - 先選「這是候選清單裡的哪一家」（預先匯入開放資料的候選清單），或「清單外的新據點」；
   - 記錄 GPS 位置、拍門面照片（照片只供內部核對，不公開）；
   - 確認是否營業、屬於哪些需求分類；
   - 逐項記錄資源：類別、項目、取得方式（可以重複新增多筆）；
   - **同意問題**：店家同不同意公開在地圖上、公開到什麼程度。不同意就標成 `private`。
   - 依前面的答案自動跳題，例如「未營業」就直接結束。
4. **上傳**：有網路時，手機會把資料傳回伺服器；沒網路時先存在手機裡。
5. **審核**：在後台檢視每一份資料，可以標記「通過、待確認、不通過」。這正好對應我們的驗證等級，例如通過的設為「現地確認」。
6. **匯出到平台**：從後台匯出 CSV 或 Excel，或用 API 讓我們的資料管線直接抓取。API 金鑰放在 `.env`，和 TDX 金鑰一樣不進 git。

### 要注意的地方
- **免費方案有使用量上限**（每月提交數、儲存空間等，數字待查核）。示範點周邊幾百份的規模應該夠用。
- **資料存在 Kobo 的伺服器上**（全球站或歐洲站）。表單只收必要資訊，不收個人聯絡方式以外的個資；師傅個人資料一律不收，技能掛在據點底下。
- **Android 與 iPhone 體驗不同**：KoboCollect 只有 Android 版；iPhone 用網頁表單，功能大致相同，但要先在有網路時載入一次。
- **團隊權限**：可以把專案分享給社團成員，分別給「填寫」「檢視」「編輯」等權限。

- `resources.inferred` 欄位區分「依來源分類推論」和「實際確認」，例如五金行推論有五金零件可買。
- 對照表的 `implied_resources` 格式是 `項目:取得方式;項目:取得方式`。
- 登記工廠沒有產業類別，所以對照表用名稱關鍵字（`factory_name_keyword`）推測，`.*` 是推測不出來時的預設。
- 驗證程式已用錯誤資料測試過：能抓出重複代碼、未定義的分類與項目、類別不符、座標超出臺北市、指向不存在的據點等問題。

## 十二、改為「不推論資源」（2026-10-27，取代第三、六、十一節中關於推論資源的部分）

**原因**：第十一節的找資源模式顯示的 9,016 筆資源，全部是依店家類別推論出來的，例如「OSM 標為木工 → 有木材邊角料可以贈送」，沒有一筆是確認過的事實。使用者希望網站資料盡可能真實可靠，所以改為：

| 層級 | 內容 | 在網站上 |
|---|---|---|
| **公開資料（參考）** | 商業登記與工廠中**高可信度**的據點，共 237 個（五金行 134、五金建材行 49、建材行 29、特定工廠 25）。只有名稱、地址、登記類別、登記年等事實 | 「公開資料（參考）」模式（原「探索鄰里」）：灰色空心點；村里概況卡列出該里的店家；店家卡註明「公開資料・未經現地確認」 |
| **確認資料** | 現地走讀確認或據點本身填寫（verification ≥ 2）的據點與資源 | 「找資源」模式；資料填入前顯示空白說明 |

實作上的改變：
- `data/schema/category_crosswalk.csv` 刪除 `implied_resources` 欄位；對照表只把來源分類對應到需求分類與中文名稱。
- `data/schema/fields.csv` 刪除 `resources.inferred`，`nodes` 新增 `category_label`（登記或標註上的類別名稱）。
- `pipeline/nodes.py` 不再產生資源，只輸出據點；`resources` 之後只來自現地與使用者（預定放在 `data/processed/field/resources_field.csv`）。
- `pipeline/build_site.py` 輸出 `nodes_verified.geojson`（確認資料）。原本的 `nodes_reference.geojson`（高可信公開資料，無資源）2026-10-31 起不再輸出，店家與工廠圖層已從網站移除。

## 十三、高可信度的定義與找資源的據點單位（2026-10-28）

### 「高可信度」是什麼
高可信度是**依規則推估「像實體店面」**，不是現地驗證過。網站上的 237 個據點組成如下：

| 組成 | 數量 | 規則 |
|---|---|---|
| 商業登記（五金零售、五金批發、建材零售） | 211 | 同時符合四個條件：① 登記狀態為「核准設立」；② 名稱含相關字詞（五金、工具、建材、水電、油漆、螺絲、鐵、金屬、木、塑膠、電料、機械、鋼、鋁、材料、門窗、衛浴、磁磚、玻璃、器材、配件、零件）；③ 地址在一樓或沒寫樓層；④ 名稱不含辦公室型字詞（貿易、國際、投資、顧問、管理、行銷、科技、資訊、地產、開發、娛樂、餐飲、生技、租賃、旅） |
| 商業登記，經 OSM 交叉比對升級 | 1 | 不符合上述規則，但 OpenStreetMap 上 30 公尺內有名稱相近的店（例如「綠光花園企業社」），兩個獨立來源都指出存在 |
| 臺北市特定工廠 | 25 | 全部標為「生產中」，且是 2020 年後才建立的登記制度，資料較新 |

另有 6 家同時符合規則與 OSM 比對。限制：規則只能排除明顯不像店面的登記，不能保證店還在、或實際賣什麼；登記工廠（870 家）因為沒有產業類別、且多在科技園區，不列入高可信度。

### 找資源以空間據點為單位
- 堆肥站從公開資料版面移除，改為「找資源」中的一個據點；「示範點」分頁刪除。
- 每個據點可以有**提供**（`resources`）與**需要**（`wants`）。堆肥站目前只有需要：需求清單中「缺、部分有、待查」的 16 項，由 `pipeline/nodes.py` 從 `nodes/ntu-compost.yaml` 輸出為 `data/processed/field/intents_field.csv`。
- `data/schema/fields.csv` 新增 `intents` 表的欄位定義（`direction` 為 need 或 offer、`status` 為缺、部分有、待查）。
- 介面上可以切換「全部、提供、需要」，需求項目以虛線框呈現並標出狀態。

## 十四、資源網絡（已確認）的據點單位與例外處理（2026-10-28）

「找資源」更名為「**資源網絡（已確認）**」，與「公開資料（參考）」對稱。不用「經驗證」，是因為資料包含兩種確認方式：

| 驗證等級 | 意思 | 例子 |
|---|---|---|
| 2 現地確認 | 團隊實際走訪、看過 | 走讀時確認某五金行有賣防腐漆 |
| 3 當事人確認 | 據點本身提供的資訊 | 堆肥站的需求清單由社團提供 |

「當事人確認」是可信的自我陳述，但不是第三方驗證，所以統稱「已確認」。介面上每個據點都會標出是哪一種。

### 原則：每個供給與需求都屬於一個空間據點
- 據點是有實際位置、可以前往或聯絡的地方：店面、工坊、社區設施、組織的據點。
- 供給記在 `resources`（取得方式：售、借、贈、服務、交換），需求記在 `intents`（`direction = need`）。
- 這讓「誰在哪裡、需要什麼、能給什麼」可以直接在地圖上呈現；之後實際發生的交換（`events`）可以畫成據點之間的連線，形成網絡。

### 例外一：沒有固定地點的資源（到府服務、貨運、搬家、行動工具車）
- **掛在提供者的聯絡據點上**：例如師傅所屬的維修中心、貨運行的店面或登記地址。
- 在資源的 `note` 註明「可到府」或服務範圍，例如「大安區、中正區可到府」。
- 如果完全沒有對外的據點（例如個人接案的貨車司機），依例外二處理。

### 例外二：個人（師傅、志工、擁有工具的居民）
- **不在地圖上標出個人的住處或精確位置**（`CLAUDE.md` 的個資原則）。
- 優先**掛在他參與的社區據點底下**：例如維修中心的志工有木作技能，就記成「維修中心：木作（服務，每週六，志工協助）」，聯絡經由該據點。
- 沒有可以掛靠的據點時，建立一個 `visibility = aggregate` 的據點，**位置只標到村里中心**，名稱用匿名描述（例如「大安區某里的木工師傅」），聯絡方式不公開，由團隊轉介。
- 一律要有本人同意才收錄，並可隨時要求移除。

### 例外三：一個組織有多個據點
- 每個實體地點各自建一個據點（例如社團的堆肥站和倉庫），供給與需求記在實際發生的地點上。
- 組織資訊（名稱、聯絡窗口）之後可以用 `agents` 表統一管理（預留，尚未實作）。
